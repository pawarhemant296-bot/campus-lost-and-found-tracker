TraceBack

Lost & Found Item Tracker

SIH Presentation & Technical Q&A Guide
A centralised, AI-assisted platform where people report lost or found items, receive smart match suggestions, prove ownership privately, chat securely and track an item all the way back to its owner. This guide covers the architecture, workflow, technology choices and the questions a jury is most likely to ask — with answers.

1Problem & objective

On any campus, in any office or public place, lost items and found items are reported through scattered WhatsApp groups, notice boards and lost-and-found desks that never talk to each other. An owner and a finder can be metres apart and never connect. TraceBack gives both sides one place to report, automatically matches lost against found, verifies the real owner, and tracks the item to a confirmed return.

Who it's for

Students, staff and visitors on a campus; adaptable to offices, transit hubs and events.

Core promise

Report once. The engine keeps scanning every new report and alerts you the moment a likely match appears.

What makes it safe

Private ownership questions and masked identities stop a stranger from simply claiming your things.

Request lifecycle

  1. The React client calls the REST API with a JWT in the Authorization header.
  2. Express validates the token, runs the route, and reads/writes SQLite through prepared statements.
  3. On a new/edited report the matching engine runs synchronously, persists any matches and fires notifications.
  4. The client polls notifications and messages so alerts appear without a page refresh.

Why one Node service (not micro-services)

A single process is far easier to run, demo and reason about under hackathon time pressure. The code is already split into clean modules (auth, items, matches, claims, …), so any one could be extracted into its own service later without a rewrite.

The matching engine is a pure, dependency-free module — it can be lifted into a separate Python/FastAPI service if heavier ML is ever needed, without touching the API contract.

5The smart matching engine

It never relies on an exact item name. It scores five independent signals, each 0–100%, and combines them with configurable weights:

Item / category similarity25%
Description similarity25%
Location similarity20%
Date / time proximity15%
Image similarity15%

The techniques, in one line each

  • Synonym lexicon — collapses phone≈mobile≈cell, wallet≈purse, canteen≈cafeteria≈mess, colour families and place names.
  • Text similarity — token overlap + Jaccard + character-bigram cosine, so typos and different wording still match.
  • Calibration curve — two people describing the same object share only 30–45% of words; a curve maps that onto human-meaningful confidence.
  • Date proximity — exponential decay across a configurable window (default 14 days).
  • Image similarity — 64-bit perceptual dHash; similarity = Hamming distance between the two hashes.
  • Weight re-normalisation — a factor with no data (e.g. no photo) is dropped and the remaining weights rescale, so scores stay comparable.

6Ownership verification & security

A major safeguard prevents anyone from simply claiming an item:

  1. The finder stores private question/answer pairs when reporting.
  2. The API returns only the questions — answers never leave the database.
  3. A claimant's answers are auto-scored against the stored answers by the same text-similarity engine.
  4. The score is advisory; the finder or an admin makes the final call.
  5. A rejected claimant can raise a dispute that lands in the admin queue.

In the demo the genuine owner scores ~89% while an impostor scores ~2%.

Privacy & security controls

  • JWT auth; passwords hashed with bcrypt.
  • Reporter names masked (Aa••• S.) and emails masked in every public response.
  • Phone numbers never serialised through the API.
  • Identities unlock only after a claim is approved.
  • Role-based access — admin routes reject non-admins (403); protected routes reject anonymous requests (401).
  • You cannot claim your own report; server-side input validation on every write.

10Anticipated jury questions & answers

Concept & impact

How is this better than a WhatsApp lost-and-found group?
A group is an unsearchable, unstructured feed with no matching, no verification and no status tracking. TraceBack structures every report, actively matches lost against found, proves ownership before handover, and shows exactly where each case stands.
Who is the target user and how do you measure success?
Students, staff and visitors on a campus. Success metrics are already in the analytics dashboard: match success rate, claim approval rate and average resolution time.

The matching engine

Is this actually "AI"? What algorithm is it?
It's a transparent, weighted multi-signal scoring model — a lightweight, explainable recommendation engine rather than a black box. Text uses token-overlap, Jaccard and character-bigram cosine with a synonym lexicon and a calibration curve; images use a perceptual difference hash. Every score is fully explainable, which is exactly what a verification workflow needs.
Why not a deep-learning / sentence-transformer model?
It's an intended upgrade path — the engine is an isolated module behind a stable interface. For a reliable, offline, instant demo, a transparent scoring model is more defensible and needs no GPU or API key. We can drop in embeddings later without changing the API.
What if there's no photo?
The image factor is marked unavailable and its 15% weight is redistributed across the remaining four, which re-normalise to 100%. A perfect text+location+time match still reaches a high score.
How do you avoid false matches?
A configurable threshold hides weak pairs, matching is one-to-many for review (not auto-confirmed), and the human verification step with private questions is the real gate before any handover.

Security & trust

What stops someone falsely claiming an item?
Private ownership questions only the true owner can answer (answers never exposed by the API), an advisory auto-score, a mandatory human decision by the finder/admin, masked identities until approval, and a dispute path for contested rejections.
How is user data protected?
Passwords are bcrypt-hashed, sessions are stateless JWTs, names/emails are masked in public responses, phone numbers are never sent, and identities are revealed only after a claim is approved.

Technical & scale

Why SQLite — will it scale?
SQLite handles thousands of concurrent readers comfortably, which covers a campus. Every query is plain SQL, so migrating to PostgreSQL for a multi-campus deployment is a driver change, not a rewrite. It was chosen for zero-setup reliability during the demo.
How would you scale to many campuses?
Swap SQLite for PostgreSQL, put the stateless API behind a load balancer, move uploads to object storage (S3/Cloudinary), and extract the matching engine into its own service if load demands it. Nothing in the design blocks this.
Real-time updates?
Today the client polls notifications and messages on a short interval — simple and demo-safe. WebSockets are the documented next step for instant push.
Is it tested?
Yes — a 44-assertion end-to-end script drives the full journey (register › report both sides › match › genuine claim vs impostor › approve › handover › returned › admin › access control), plus an automated screenshot pass across three screen sizes.

Product & future

What would you add next?
College email verification, map-based location matching (haversine on coordinates), WebSocket push, sentence-transformer text embeddings, and a native mobile app.
